# Local review-assisted lyrics

**Current flow (2026-10-08, supersedes the per-syllable form described further down, which is now the
"Place syllables by hand (advanced)" section).** Each row's card shows the lyric row with its staff and numbered
lines for the recognised notes around it (the proposed notes in blue), a text box under each
recognised notehead (numbered like the picture; filled where a syllable is proposed, blank elsewhere), and the lyric
line. To split a word, put its parts in neighbouring boxes; to move one, clear a box and type in another. **Accept** means the text, lyric line
and notes shown are right (any edit withdraws it). "Accept all suggested rows" is a shortcut: it accepts the suggested lyrics and also the
directions and dynamics that already have a proposed note (rows with no proposed note stay for you to place). "Add accepted lyrics
and staff text to the score" lists exactly what will be written; "Add to the score" saves it (no separate confirmation tick: the
list is the review)
as the page's reviewed score, so the scan's MusicXML (job-level download, combined score) carries the lyrics and the
engine's own recognition output stays untouched. Saving again replaces the lyrics a previous save added.
"Download a copy instead" produces the file without changing the scan. Later token-level note corrections on the
page regenerate its score and drop the lyrics, so correct notes first. Routes: `crop?view=placement`,
`POST .../save-lyrics`.


The page-specific scanner lyric review (`/scanner/<job>/pages/<page>/lyric-review`)
can now create a download containing explicitly reviewed syllables. It remains
behind both existing flags: `NEXT_PUBLIC_OTS_HOMR_LYRIC_REVIEW_ENABLED=1` and
`SCANNER_OTS_HOMR_LYRIC_REVIEW_ENABLED=1`. This change does not enable either flag,
change provider/model pins, deploy, or invoke a recognition provider.

1. Check the full scan and detected region; correct and accept the region's text.
2. Use **Add N proposed syllables from accepted rows** to bring in the scanner's proposals: each accepted,
   unedited row's syllables arrive with the exact recognised note they point at (the page's decoded tokens
   are aligned with the MusicXML note elements; a part that does not align exactly gets no proposals) and
   the printed line, all **unconfirmed**. When several proposals land on one note and line only the nearest
   is proposed; the rest are for you to place by hand. Or add each syllable yourself: Select its actual recognised-score
   note and the printed lyric line (top to bottom). Note labels identify source
   part, displayed and physical measure, quarter-note offset, pitch, staff and voice.
   Accepted, unchanged rows with a note alignment may propose syllables and exact
   XML note choices. These proposals still require all three confirmations.
3. Confirm syllable text, printed line and note placement independently. Editing
   a field withdraws its confirmation. Accepting a region alone never attaches it.
4. Download the validated score copy and optionally export its confirmed placement
   plan. Drafts survive refresh only for the same page, raster and MusicXML hashes.

The full recognition raster and original recognised MusicXML remain available
for context. The downloaded copy adds text-only `<lyric>` elements numbered by
explicitly selected printed line. **Hyphenation, melismas, and native verse-number
mapping are not generated by this feature.** They need subsequent editing; this
is not unattended attachment or full lyric-notation completion.

## Read-only API contract

All routes require the existing scanner availability gate, authenticated job
ownership and lyric-review feature flag.

- `GET .../lyric-candidates/scan`: hash/dimension-checked full recognition PNG.
- `GET .../lyric-candidates/notes`: current XML SHA-256 plus actual pitched note
  choices. Note ordinals include preceding rests and chords, as MusicXML does.
- `POST .../lyric-candidates/corrected-copy`: request must include current XML and
  raster hashes, `automaticAttachment: false`, and 1–1000 explicit placements.
  Each placement binds a current candidate ID, unique placement ID, actual note
  ID, nonempty corrected syllable, printed line 1–20, and all three confirmations.

The writer refuses stale identities, unknown candidates/notes, incomplete
confirmations, duplicate or already occupied note/line slots, unsafe XML, and any
change to non-lyric score content. Existing lyrics are preserved. The service
returns a private, noncached attachment and does not store or overwrite a score,
create a source revision, or publish anything.

## Validation

- Backend focused suites exercise the copy writer, service gate/raster binding,
  original-score preservation, escaping, duplicates, occupied slots and controller.
- Frontend focused suites exercise explicit confirmation, edit invalidation,
  authenticated proxy payload and download, plus existing candidate review.
- `smoke/e2e/scanner-lyric-copy.spec.cjs` exercises a completed local fixture through
  the real browser/proxy/backend. Opt in with `LYRIC_COPY_SMOKE=1`,
  `LYRIC_COPY_JOB_ID`, `LYRIC_COPY_OWNER_EMAIL`, optional `LYRIC_COPY_PAGE` and the
  local session secret. It does not upload or scan a new page and checks the stored
  XML hash after download remains unchanged.

## Entry point and end-to-end test

On the scan's job page, a page whose OTS-HOMR run produced a text review shows **Review lyrics and staff text for this page**
(same flag as the review page). The upload form's **This score has lyrics** box (needs
`NEXT_PUBLIC_OTS_HOMR_FUSION_ENABLED=1` and `SCANNER_OTS_HOMR_FUSION_ENABLED=1`) is what makes the scan run
fusion-v1, OCR and the text classifier.

`smoke/e2e/scanner-lyric-checkbox-flow.spec.cjs` drives the whole path in a real browser: upload with the box
ticked, start, wait, open the review, accept the suggested rows, add the proposals, confirm each, download, then
check the copy is a new document with the original's non-lyric content unchanged. Opt in with
`LYRIC_FLOW_SMOKE=1`, `LYRIC_FLOW_OWNER_EMAIL` and `LYRIC_FLOW_IMAGE` (costs one provider scan) or
`LYRIC_FLOW_JOB_ID` (re-runs the review half on a completed local job). Its confirmations are clicked by the test:
a fixture, not a person's approval.

The 2026-10-08 run of this flow on a real GPU scan of IMSLP10602 produced 18 OCR rows, 17 suggested, 26 proposals
(25 after the one-syllable-per-note rule) and a 25-lyric copy whose non-lyric content was identical to the
recognised score. A draft-restore race that wiped added rows and an unfiltered same-note proposal (the writer refused
the whole copy, 409) were found and fixed by that run.
